# 발헤임 1.0 데디케이티드 서버 + 관리 웹앱 설계

작성일: 2026-09-17

## 1. 개요

발헤임 1.0 데디케이티드 서버를 GCP 무료 체험판 위에 구축하고, 친구들이 문제없이 참여할 수 있도록 서버 기동과 모드팩 배포를 담당하는 웹앱을 함께 만든다.

서버는 평소 정지 상태로 두고, 방장이 웹앱에서 켜거나 예약해 두면 기동한다. 아무도 접속하지 않으면 스스로 종료해 크레딧을 아낀다.

## 2. 배경 사실 (2026-09-17 기준 조사 결과)

### 2.1 발헤임 1.0

- 2026년 9월 9일 정식 출시. 빌드 25185644, 게임 내 표기 `l-1.0.7`, 네트워크 버전 39
- 9월 11일 핫픽스 1.0.10 (전 플랫폼), 1.0.12 (Steam)
- 구버전 서버(0.221.12, 네트워크 36)에는 1.0 클라이언트가 접속할 수 없다
- Deep North 추가, PS5 및 Switch 2 지원, 전 플랫폼 크로스플레이 도입

### 2.2 크로스플레이와 모드는 양립 불가

크로스플레이를 켜면 게임이 Steam 네트워킹 대신 PlayFab 네트워킹을 사용한다. BepInEx는 Steam 경로에 후킹하므로 둘을 동시에 쓸 수 없다.

**결정: 크로스플레이를 끄고 BepInEx 모드를 채택한다.** 참여자 전원이 Steam PC 유저이므로 손실이 없다.

### 2.3 모드 생태계 현황

- `BepInExPack_Valheim` 5.4.2350: 출시 당일(9/9) 1.0 대응 완료
- `Jotunn` 2.30.0: 약 5,500개 모드가 의존하는 공용 라이브러리, 9/9 대응 완료
- Thunderstore "Deep North Update" 태그 모드: 9/11에 약 291개, 최근 조회 시 약 576개로 증가 중 (정확한 집계 시점은 출처에 명시되지 않음)
- 9월 13일 기준 전체 모드의 약 3분의 1이 1.0 빌드를 냈다

**모드 목록은 며칠 단위로 낡는다. 이 문서의 버전 번호를 그대로 믿고 설치하면 안 된다.**

### 2.4 GCP 무료 체험판 제약

| 제약 | 설계 반영 |
|---|---|
| $300 크레딧 / 90일, 먼저 끝나는 쪽에서 종료 | 온디맨드 운영으로 사용량 최소화 |
| 체험판 종료 시 워크로드 셧다운 | 월드 정본을 VM이 아닌 GCS 버킷에 보관 |
| 체험판 중 할당량 증설 요청 불가 | 4 vCPU만 사용, 기본 할당량 내 |
| GPU, Windows Server, Marketplace 불가 | Linux + Docker Hub 이미지 사용, 해당 없음 |
| 만료 시 자동 결제 없음, 그냥 정지 | 유료 전환은 명시적 선택 |

체험판이 막는 것 중 본 설계를 저해하는 항목은 없다.

## 4. 서브프로젝트 분해

| # | 이름 | 범위 | 의존 |
|---|---|---|---|
| A | 인프라 및 게임 서버 | GCP VM, 컨테이너, 백업, 자가 종료 | 없음 |
| B | 모드 스택 | 서버측 모드, 클라이언트 모드팩 배포 | A |
| C | 관리 웹앱 | 상태 표시, 기동, 예약, 모드팩 안내 | A, B |

각 서브프로젝트는 독립적으로 구현하고 검증한다. A가 동작하지 않으면 B와 C는 의미가 없으므로 순서를 지킨다.

**구현 계획은 A를 먼저 단독으로 다룬다.** B와 C는 A가 실물로 검증된 뒤 별도 계획으로 작성한다. 세 개를 한 계획에 묶으면 실패 지점을 구분할 수 없다.

## 5. 서브프로젝트 A: 인프라 및 게임 서버

### 5.1 VM 사양

| 항목 | 값 | 근거 |
|---|---|---|
| 리전 | `asia-northeast3` (서울) | 참여자 전원 한국 거주, 실시간 전투 레이턴시 |
| 머신 타입 | `n2-standard-4` (4 vCPU / 16GB) | 8명 + 콘텐츠 모드 시 10~12GB 권장. 발헤임 시뮬레이션은 싱글스레드 중심이라 클럭이 중요하며 n2가 e2보다 유리 |
| 디스크 | Balanced PD 50GB | 게임 약 4GB + 월드 + 백업 여유 |
| 외부 IP | 고정 IP | 친구들이 Steam 즐겨찾기에 등록 가능 |
| 방화벽 | UDP 2456-2458만 개방 | 그 외 전부 차단 |
| 관리 접속 | IAP 터널 | SSH 포트를 인터넷에 노출하지 않음 |

VM은 정지 상태에서 머신 타입 변경이 가능하므로 성능이 부족하면 상향할 수 있다.

> **주의**: 체험판은 할당량 증설을 요청할 수 없다. 리전당 기본 vCPU 할당량이 8인 경우 `n2-standard-8`(8 vCPU)은 천장에 정확히 닿아 실패할 수 있다. 상향이 필요해지면 먼저 콘솔에서 실제 할당량을 확인할 것. (U8)

### 5.2 비용 추정

하루 4시간 가동(90일간 360시간) 기준.

| 항목 | 90일 추정 |
|---|---|
| VM 360시간 | 약 $89 |
| 디스크 50GB | 약 $17 |
| 고정 IP (미사용 시간 과금 포함) | 약 $19 |
| GCS 백업 | 약 $1 |
| Cloud Run, Firestore, Cloud Scheduler | 약 $0 (무료 한도 내) |
| **합계** | **약 $127** |

크레딧 $300의 약 42%. 하루 8시간씩 써도 여유가 있다.

> **검증 필요**: 서울 리전 단가는 추정치다. 가격 페이지 조회에 반복 실패해 실시간 검증을 하지 못했다. 구축 전 GCP 가격 계산기와 콘솔 실물로 확인할 것.

참고로 24/7 가동은 시간이 6배(2160시간)가 되어 16GB 구성이 예산을 초과한다. 온디맨드를 택한 덕분에 더 좋은 사양을 쓸 수 있다.

### 5.3 게임 서버 컨테이너

`community-valheim-tools/valheim-server-docker` (구 `lloesche/valheim-server-docker`) 이미지를 사용한다. 1.0을 정식 지원하며 1.0에서 바뀐 월드 디렉터리 구조 변환을 처리한다.

주요 설정:

| 설정 | 값 | 이유 |
|---|---|---|
| `BEPINEX` | `true` | 모드 스택 |
| 크로스플레이 | 끔 | 모드와 양립 불가 |
| `SERVER_PUBLIC` | `true` | Steam 쿼리로 인원 수를 읽으려면 필요. 비밀번호 보호는 유지 |
| `STATUS_HTTP` | `true`, localhost 바인딩 | 외부 포트 노출 없이 내부에서만 읽음 |
| `BACKUPS_CRON` | 시간별 | 이후 GCS로 동기화 |
| `UPDATE_CRON` | **비활성** | 자동 업데이트 금지 (7.2절 참조) |

### 5.4 상태 전달 경로

Cloud Run은 아웃바운드 UDP를 지원하지 않는다. 따라서 웹앱이 Steam 쿼리를 직접 발신하는 방식은 불가능하다. VM의 HTTP 상태 포트를 인터넷에 개방하는 것도 바람직하지 않다.

**해결: 방향을 뒤집어 VM이 밖으로 push한다.**

```
VM (1분 주기)
  1. localhost의 status.json 조회 (접속 인원, 서버명, 월드, 빌드 ID)
  2. Firestore 문서에 heartbeat 기록
        |
        v
  Cloud Run 웹앱은 Firestore를 읽기만 한다
```

이 구조 덕분에 게임 포트(UDP 2456-2458) 외에 인터넷에 열리는 포트가 하나도 없고, 웹앱과 VM 사이에 직접 네트워크 경로가 필요 없다.

### 5.5 자가 종료 (`idle-guard`)

VM 내부에서 1분 주기 systemd 타이머로 동작한다.

```
기동 후 15분 이내인가?          -> 아무것도 하지 않음 (유예 시간)
접속 인원 > 0 인가?             -> 유휴 카운터 리셋
접속 인원 0이 20분 지속되었나?  -> 1. docker stop (월드 저장 보장)
                                   2. GCS로 백업 동기화
                                   3. shutdown -h now
```

VM이 TERMINATED 상태가 되면 컴퓨트 과금이 중지된다 (디스크와 고정 IP는 계속 과금).

**기동 후 15분 유예가 필요한 이유**: 유예가 없으면 켜자마자 꺼진다.

**`idle-guard`는 어떤 외부 서비스에도 의존하지 않는다.** Firestore가 장애를 겪든, 웹앱 배포가 잘못되든, Cloud Run이 죽든 서버는 정확히 스스로 종료한다. 비용이 새는 사고를 구조적으로 차단하는 것이 이 설계의 목적이다.

### 5.6 백업

1. 컨테이너 내장 백업이 시간별로 `/config/backups`에 생성
2. 별도 systemd 타이머가 GCS 버킷으로 동기화
3. 종료 직전에도 1회 동기화

**월드의 정본은 VM 디스크가 아니라 GCS 버킷이다.** 체험판 만료 시 워크로드가 셧다운되므로 이 분리가 필수다.

## 6. 서브프로젝트 B: 모드 스택

### 6.1 3계층 분류

모든 모드가 클라이언트 설치를 요구하지는 않는다.

| 계층 | 설치 위치 | 친구가 할 일 | 버전 통일 |
|---|---|---|---|
| 1층 | 서버 전용 | 없음 | 불필요 |
| 2층 | 클라이언트 개별 | 원하는 사람만 설치 | 불필요 |
| 3층 | 서버 + 전 클라이언트 | 모드팩 코드 적용 | **필수** |

**설계 원칙: 1층에서 해결되는 기능은 3층으로 올리지 않는다.** 3층 모드가 하나라도 있으면 전원이 버전을 맞춰야 하고, 한 명만 어긋나도 그 사람은 접속하지 못한다. 모드 개수가 아니라 3층의 존재 여부가 운영 난이도를 결정한다.

### 6.2 모드팩 v1

**1층 (서버 전용, 친구 설치 불필요)**

| 모드 | 작성자 | 버전 | 상태 |
|---|---|---|---|
| `ServersideQoL` | ArgusMagnus | 2.0.13 | Deep North 태그 확인 |
| `PlantEverything` | Advize | 1.21.2 | Deep North 태그 확인 |

`ServersideQoL` 제공 기능: 제련소 및 가마에 근처 상자에서 자동 연료/재료 공급, 인벤토리 일괄 보관, 상자 자동 정렬, 포탈 허브 생성.

> **설정 주의**: 이 모드에는 "무한 건축/농사 스태미나" 기능이 포함되어 있다. 난이도 저하에 해당하므로 config에서 비활성화한다.

**3층 (모드팩 필수)**

| 모드 | 작성자 | 버전 | 비고 |

| `PlanBuild` | MathiasDecrock | 0.18.5 | 건축 청사진 |
| `MultiUserChest` | MSchmoecker | 0.6.2 | 여러 명이 같은 상자 동시 사용 |

### 6.3 인벤토리 모드 충돌 경고

`EquipmentAndQuickSlots`, `AzuExtendedPlayerInventory`, `ExtraSlots` 세 모드는 동일한 인벤토리 컨테이너 메서드를 패치한다. 둘 이상을 함께 설치하면 슬롯이 늘어나는 것이 아니라 **슬롯 참조가 손상되고 재접속 시 아이템이 소실된다.**

**반드시 셋 중 하나만 설치한다. 본 설계는 `ExtraSlots`를 선택했다.**

친구들이 개별적으로 다른 인벤토리 모드를 추가하지 않도록 모드팩 안내에 이 경고를 명시한다.

### 6.4 대기 목록 (1.0 대응 시 재검토)

| 항목 | 현황 |
|---|---|
| **작업대 제작 시 근처 상자 자원 사용** | 최우선 요청 사항. `Grizzzly/CraftFromContainers`는 Deprecated, `rendl0449/CraftFromContainers`는 Ashlands/Bog Witch 태그까지만, `AzuCraftyBoxes`는 8월 이후 릴리스 없음. **1.0 대응 구현을 찾지 못했다** |

| 콘텐츠 모드 (`Monstrum Deep North` 등) | 난이도를 높이는 방향이므로 기준에 위배되지 않음. 3단계에서 검토 |

### 6.5 제외한 모드

난이도를 낮추거나 엔드게임 파워 스케일링을 추가하는 모드는 요구사항에 따라 제외한다.

- `Epic Loot` (랜덤 매직 드롭, 5단계 희귀도)
- `Jewelcrafting` (젬 소켓 파워 스케일링)
- `ValheimPlus` 계열의 배수 설정, 무게 제한 증가, 포탈 금속 운반 허용, 사망 페널티 제거

### 6.6 모드팩 배포 방식

```
방장: r2modman 또는 Thunderstore Mod Manager에서 프로필 구성
      -> "프로필 공유" -> 코드 발급

친구: r2modman 설치 -> 코드 붙여넣기 -> 동일 모드셋 자동 구성
```

친구가 할 일은 코드 하나를 붙여넣는 것뿐이다.

**웹앱이 항상 최신 코드를 표시한다.** 메신저로 코드를 배포하면 옛 코드를 쓰는 사람이 반드시 생긴다. 단일 출처를 유지하는 것이 목적이다.

### 6.7 단계적 도입

1. **1단계**: 1층만 구성해 안정화. 친구들은 바닐라 클라이언트로 즉시 접속
2. **2단계**: 며칠 운영 후 필요한 3층 모드를 추가
3. **3단계**: 1.0 대응이 성숙한 뒤 콘텐츠 모드 검토

**모드 문제와 인프라 문제를 동시에 겪지 않는 것이 이 순서의 목적이다.** 처음부터 모드를 다수 얹으면 서버가 뜨지 않을 때 원인이 GCP인지 모드인지 구분할 수 없다.

## 7. 서브프로젝트 C: 관리 웹앱

### 7.1 구성 요소

| 단위 | 위치 | 책임 | 의존 |
|---|---|---|---|
| 웹앱 | Cloud Run | 화면 렌더링, 기동/종료/예약 API | Firestore, Compute API |
| `heartbeat` | VM 내부 | 1분 주기로 상태를 Firestore에 push | Firestore |
| `idle-guard` | VM 내부 | 유휴 판정 후 안전 종료 | **없음** |
| `scheduler` | Cloud Scheduler | 5분 주기로 예약 도래 질의 | 웹앱 |
| `update-checker` | Cloud Scheduler | 일 1회 Steam 최신 빌드 조회 | 웹앱 |

`idle-guard`가 무의존인 것이 안전성의 핵심이다 (5.5절 참조).

### 7.2 업데이트 알림

컨테이너 자동 업데이트를 끈 상태로 운영한다. 자동 업데이트를 켜두면 다음 사고가 무인 상태에서 발생한다.

```
Iron Gate가 신규 빌드 배포
  -> Steam이 친구들 클라이언트를 자동 업데이트
  -> 서버는 구버전이라 전원 접속 불가
  -> 급히 서버를 업데이트
  -> 모드가 신규 빌드 미대응이라 서버가 기동하지 않음
```

1.0 출시 후 이틀 만에 1.0.7 -> 1.0.10 -> 1.0.12로 진행되었다. 초기에는 핫픽스 빈도가 높다.

**대응:**

```
일 1회: Steam에서 발헤임 데디케이티드 서버(앱 ID 896660) 최신 빌드 ID 조회
        -> heartbeat이 보고한 현재 설치 빌드 ID와 비교
        -> 상이하면 Firestore에 기록
        -> 웹앱에 배너 표시: "서버 업데이트 있음 (방장만 실행 가능)"
```

실행은 방장이 명시적으로 누를 때만 이루어지며, 실행 전 백업을 강제한다.

### 7.3 권한 모델

| 기능 | 비밀 URL만 | + 방장 비밀번호 |
|---|---|---|
| 상태, 접속 주소, 인원 조회 | O | O |
| 모드팩 코드 및 설치 안내 조회 | O | O |
| 서버 기동 / 종료 | X | O |
| 예약 등록 / 삭제 | X | O |
| 업데이트 실행 | X | O |

- 비밀번호는 Secret Manager에 해시로 보관하고, 통과 시 세션 쿠키를 발급한다
- 비밀 URL은 추측 불가능한 길이의 경로를 사용한다
- `noindex` 메타와 `robots.txt`로 검색 노출을 차단한다
- Cloud Run의 서비스 계정은 `compute.instances.get/start/stop`만 갖는 최소 권한으로 구성한다

### 7.4 예약

예약마다 Cloud Scheduler 작업을 생성하지 않는다. 5분 주기로 한 번 질의하는 방식이 단순하고, 5분 해상도면 충분하다.

```
방장이 "금요일 20:00" 등록  ->  Firestore에 저장
Cloud Scheduler가 5분마다 웹앱에 질의  ->  도래한 예약이 있으면 VM start
```

Cloud Scheduler에서 웹앱 호출 시 OIDC 토큰으로 인증한다.

### 7.5 Firestore 데이터 모델

| 문서 | 필드 |
|---|---|
| `server/state` | `vmStatus`, `containerStatus`, `playerCount`, `players[]`, `gameBuildId`, `ip`, `idleSince`, `updatedAt` |
| `schedules/{id}` | `startAt`, `note`, `executed`, `createdAt` |
| `modpack/current` | `version`, `r2modmanCode`, `mods[]`, `updatedAt` |
| `updates/available` | `latestBuildId`, `currentBuildId`, `updateAvailable`, `checkedAt` |

### 7.6 에러 처리

| 상황 | 대응 |
|---|---|
| 여러 명이 동시에 기동 요청 | 멱등 처리. 이미 기동 중이면 무시하고 진행 상태만 반환 |
| heartbeat 2분 이상 중단 | "상태 불명" 표시 후 Compute API로 VM 상태를 직접 조회 (fallback) |
| VM 기동 실패 (할당량, 리소스 부족) | **에러 원문을 그대로 노출한다.** "알 수 없는 오류"는 디버깅을 불가능하게 만든다 |
| 예약 실행 실패 | 실패를 기록하고 다음 폴링에서 재시도 |
| VM은 동작하나 컨테이너가 중단됨 | heartbeat에 컨테이너 상태를 포함해 웹앱이 "서버 프로세스 이상" 경고 표시 |
| 모드팩 버전 불일치로 접속 실패 | 웹앱에 서버 빌드와 모드팩 버전을 상시 표시해 사전 확인 가능하게 함 |

### 7.7 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 웹앱 | Next.js (TypeScript) + Cloud Run | Cloud Run 배포가 정형화되어 있고 기능 확장이 용이 |
| VM 스크립트 | Bash + systemd 타이머 | 런타임 의존성 최소화. `idle-guard`의 신뢰성에 직결 |
| 상태 저장 | Firestore | 무료 한도 내, 단순한 문서 모델로 충분 |
| 예약 트리거 | Cloud Scheduler | 관리형, 무료 한도 내 |
| 백업 저장소 | Cloud Storage | 체험판 만료 후 이전 경로 확보 |

## 8. 디자인 방향

### 8.1 제약

1. **좌측 사이드바 금지**
2. **상단 띠(바) 형태 금지**
3. **em dash 사용 금지** (UI 문구 및 문서 전반)

### 8.2 방향

- **레이아웃**: 중앙 정렬 카드 스택. 화면 중앙에 서버 상태를 주인공으로 배치하고 그 아래로 접속 정보, 모드팩, 컨트롤을 쌓는다
- **우선순위**: 모바일 우선. 친구들이 휴대폰으로 열어볼 가능성이 높다
- **톤**: 발헤임의 북유럽 정서에 맞춘 어두운 배경과 청동빛 악센트. 다크 모드 기본
- **정보 위계**: 접속 상태 > 접속 주소 > 인원 > 모드팩 > 컨트롤
- **상태 표현**: 정지, 기동 중, 실행 중, 종료 중을 색과 문구로 명확히 구분. 기동 중에는 예상 대기 시간을 표시한다

```

        접속 주소   34.64.123.45:2456   [복사]
        비밀번호    ********             [복사]

        접속자   Odin · Thor · Freya
```

## 10. 90일 이후 출구 전략

체험판 종료 시 게임 서버와 웹앱이 함께 정지한다. Cloud Run이 상시 무료 한도 내에 있어도 결제 계정이 종료되면 그 위의 모든 리소스가 정지한다. 웹앱만 별도로 존속하지 않는다.

| 선택 | 결과 | 비용 |
|---|---|---|
| 유료 계정 전환 | 전부 유지 | 게임 서버 월 약 $25, 웹앱 거의 0 |
| 아무 조치 없음 | 정지 후 데이터 삭제 | 0 |
| 백업 회수 후 종료 | 월드 파일 확보 후 정리 | 0 |

세 번째 선택지가 가능하려면 백업이 GCS에 있어야 하며, 이것이 5.6절 설계의 이유다.

설정을 코드로 남겨 다른 환경(타 클라우드, 개인 PC)으로 이전할 수 있게 한다.

## 12. 검증 방법

| 대상 | 방법 |
|---|---|
| 웹앱 로직 | 단위 테스트. 예약 도래 판정, 권한 체크, 멱등성, 빌드 ID 비교. Compute API는 목킹 |
| `idle-guard` | `status.json` 픽스처로 유휴 판정 검증. 실제 종료는 dry-run 플래그로 분리 |
| `heartbeat` | Firestore 에뮬레이터로 기록 검증 |
| 통합 | **실물 필수**: 기동 -> 접속 -> 퇴장 -> 20분 후 자동 종료 전 과정을 실제로 1회 확인 |
| 모드 스택 | 서버 기동 로그에 모드 로딩 확인, 클라이언트 1대로 실제 접속 확인 |
| 백업 | GCS 버킷에서 월드를 내려받아 별도 환경에서 복원 성공 확인 |
