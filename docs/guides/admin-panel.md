# 관리 패널 가이드

작성일: 2026-09-18

방장이 서버 PC 에서 여는 로컬 웹 패널이다. 친구용 사이트(`web/`)와 달리 **배포물이 아니다.** 도커를 조작해야 하므로 서버 PC 에서만 돌고, 인터넷에도 사내망에도 올리지 않는다.

`docs/superpowers/specs/2026-09-18-mod-portal-web-design.md` 의 9절이 정한 구성 중 서버 제어, 드리프트 감지, 로그, 백업을 구현했다.

## 한눈에 보기

| 항목 | 값 |
|---|---|
| 실행 | `node admin/server.mjs` |
| 주소 | `http://127.0.0.1:4330` |
| 포트 바꾸기 | `ADMIN_PORT=4331 node admin/server.mjs` |
| 컨테이너 이름 바꾸기 | `VALHEIM_CONTAINER=이름 node admin/server.mjs` |
| 런타임 의존성 | 없음. `node:http` 와 `node:child_process` 만 쓴다 |
| 종료 | 실행한 터미널에서 Ctrl+C |

친구 사이트 개발 서버가 4321 을 쓰므로 겹치지 않게 4330 을 골랐다.

# 절대 외부에 열지 않는다

**이것이 이 패널에서 가장 중요한 규칙이다.**

패널에는 로그인이 없다. 대신 **서버 PC 본인만 접근할 수 있다**는 것을 유일한 보호 장치로 삼는다. 이 전제가 깨지면 보호가 통째로 사라진다.

패널이 할 수 있는 일을 보면 이유가 분명하다.

- 서버를 중지하고 재시작한다. 플레이 중인 친구 전원이 끊긴다
- 컨테이너 안의 파일 목록과 설정 파일 이름을 읽는다
- 컨테이너 로그 전체에 접근한다

외부에 열려 있으면 **누구나 버튼 하나로 서버를 끌 수 있다.** 인증을 붙이지 않은 이유는, 방장 혼자 쓰는 도구에 인증 체계를 얹는 것보다 아예 외부에서 닿지 못하게 하는 편이 단순하고 확실하기 때문이다.

## 코드가 강제하는 것

| 방어 | 내용 |
|---|---|
| 바인딩 주소 | `127.0.0.1` 로 고정. **설정 항목이 아니다.** 코드에 박아 두었다 |
| Host 헤더 검사 | `127.0.0.1:포트`, `localhost:포트`, `[::1]:포트` 가 아니면 403 |
| CORS | 헤더를 아예 내보내지 않는다. 다른 출처의 페이지가 응답을 읽지 못한다 |

Host 헤더 검사가 따로 있는 이유는 **DNS 리바인딩** 때문이다. 바인딩만으로는 부족하다. 공격자가 자기 도메인을 `127.0.0.1` 로 가리키게 해 두면, 그 도메인을 연 브라우저가 이 서버에 요청을 보낼 수 있다. 그때 Host 헤더는 공격자 도메인이므로 거기서 걸린다.

## 하면 안 되는 것

- 라우터에서 4330 포트를 포워딩한다
- 바인딩 주소를 `0.0.0.0` 으로 바꾼다
- 리버스 프록시를 앞에 두고 도메인을 붙인다
- 다른 PC 에서 쓰려고 SSH 터널 없이 노출한다

다른 PC 에서 꼭 써야 한다면 SSH 포트 포워딩으로 `127.0.0.1:4330` 을 그 PC 의 로컬 포트에 붙인다. 그것이 유일한 안전한 방법이다.

# 실행

Git Bash 에서 `package.json` 이 있는 디렉터리로 `cd` 하면 fnm 별칭 문제로 오류가 나므로 저장소 루트에서 그대로 실행한다.

```bash
cd /c/Users/SangHyeonLee/orca/valheim-multi
node admin/server.mjs
```

이런 출력이 나오면 성공이다.

```
발헤임 관리 패널
주소      http://127.0.0.1:4330
컨테이너  valheim
비밀값    1개를 로그 가리기용으로 읽었다 (값은 화면에 나가지 않는다)

이 서버는 127.0.0.1 에만 붙어 있다. 외부에 열지 않는다.
종료하려면 Ctrl+C
```

브라우저에서 `http://127.0.0.1:4330` 을 연다. `localhost` 로 열어도 된다.

패널은 상시 실행할 필요가 없다. 친구들에게 상태를 보여주는 것은 별도 프로세스인 `agent/status-publisher.mjs` 가 맡는다(`docs/guides/status-publisher-setup.md`). 패널은 필요할 때 켜고 끝나면 끈다.

# 서버 탭

현재 상태와 시작, 중지, 재시작 버튼이 있다.

| 표시 | 의미 |
|---|---|
| 가동 중 | 컨테이너가 돌고 있고 `status.json` 이 정상 응답한다. 친구가 접속할 수 있다 |
| 컨테이너는 떴지만 아직 접속을 받지 못한다 | 기동 중이다. 보통 1~2분 걸린다 |
| 중지됨 | 컨테이너가 멈춰 있다 |

접속 인원은 컨테이너 안의 `status.json` 의 `player_count` 에서 읽는다. 상태 HTTP 는 호스트에 노출되어 있지 않아 `docker exec` 로만 읽을 수 있다.

## 접속자가 있으면 한 번 더 묻는다

중지와 재시작을 누르면 확인 창이 뜬다. **접속자가 있으면 문구가 달라지고 인원 수를 알려 준다.** 사람이 플레이 중인데 말없이 끊으면 안 되기 때문이다.

확인은 두 겹이다. 화면에서 한 번 묻고, 서버가 요청을 받은 직후에 접속 인원을 **다시 읽어서** 판정한다. 화면에 뜬 숫자는 최대 4초 낡았을 수 있어서, 확인 창을 띄운 사이에 누가 들어왔다면 서버 쪽에서 한 번 더 막고 다시 묻는다.

## 완료를 어떻게 판정하는가

재시작은 시간이 걸린다. 진행 상황이 단계별로 화면에 쌓인다.

```
재시작 진행 중
  20:51:03  컨테이너를 재시작한다. 월드 저장 유예로 최대 2분 걸린다
  20:52:44  컨테이너가 올라왔다. 서버가 접속을 받을 때까지 기다린다
  20:54:12  서버가 응답하기 시작했다 (18번째 확인)
  재시작 완료
```

**"컨테이너가 running" 만으로는 완료로 보지 않는다.** 컨테이너는 몇 초 만에 뜨지만 발헤임이 월드를 올리고 접속을 받기까지는 1분 넘게 걸린다. 그 사이에 완료라고 말하면 거짓말이 된다.

완료 판정은 **컨테이너 안의 `status.json` 이 `error` 없이 응답하는 것**이다. 이것이 곧 Steam 쿼리에 답할 수 있는 상태이고, 친구가 접속할 수 있는 상태다. 5초 간격으로 확인하며 5분까지 기다린다. 그 안에 응답하지 않으면 그렇다고 적고 멈춘다. 로그 탭에서 원인을 본다.

중지에는 `docker stop -t 120` 을 쓴다. compose 의 `stop_grace_period` 가 2분인 것과 맞춘 값이다. 기본값인 10초로 끊으면 월드 저장 도중에 죽어 월드가 손상될 수 있다.

## 실패하면 원문을 보여준다

docker 명령이 실패하면 `stderr` 원문을 그대로 화면에 띄운다. "알 수 없는 오류" 는 디버깅을 막는다. 다만 비밀값 가리기는 통과시킨다.

# 모드 대조 탭 (드리프트 감지)

**이 패널을 만든 가장 큰 이유다.**

`data/mods.json` 이 **선언한 것**과 서버에 **실제로 깔린 것**을 비교한다.

## 왜 필요한가

실제로 겪은 사고가 있다. `ServersideQoL` 이 로그에 이렇게 떴다.

```
[Info   :   BepInEx] Loading [ServersideQoL 2.0.13]
```

로그만 보면 정상이다. 그런데 패처 DLL 이 없어서 **config 파일조차 만들지 못한 채 기능이 전부 죽어 있었다.** `Loading` 은 "DLL 을 읽었다" 일 뿐 "동작한다" 가 아니다.

이 상태를 잡아내려고 만든 기능이다.

## 판정표

| 선언 | 실제 | 판정 |
|---|---|---|
| 있음, 버전 일치 | 로드됨, config 있음 | 정상 |
| 있음 | 파일 없음 | 미설치 |
| 있음 | 파일 있음, 로드 기록 없음 | 로드 안 됨 |
| 있음, 버전 다름 | 로드됨 | 버전 불일치 |
| 없음 | 로드됨 | 유령 모드 |
| 있음 | 로드됨, **config 없음** | **초기화 실패** |

마지막이 위 사고에 해당한다. 스펙 7절의 다섯 가지에 "로드 안 됨" 을 하나 더했다. 파일은 있는데 로드 기록이 없는 상태를 "미설치" 로 뭉뚱그리면 원인을 찾을 때 엉뚱한 곳을 보게 되기 때문이다.

## 무엇을 근거로 판정하는가

| 근거 | 읽는 곳 |
|---|---|
| 파일 존재 | `docker exec valheim ls -1 /config/bepinex/plugins` |
| 로드 여부와 실제 버전 | 컨테이너 로그의 `Loading [이름 버전]` |
| config 존재 | `docker exec valheim ls -1 /config/bepinex/*.cfg` |

로그는 **컨테이너 시작 시각 이후**만 읽고, 그중에서도 **마지막 `N plugins to load` 뒤**만 본다. 재시작하면 같은 로그에 기동 블록이 쌓이는데, 앞의 것을 읽으면 이미 지운 모드가 살아 있는 것처럼 보인다.

표 위에는 `patcher N개 로드` 도 함께 띄운다. `1개` 면 BepInEx 자체 패처만 로드된 것이라 위 사고가 재발했다는 신호다. `2개` 가 정상이다.

## 어떤 모드를 대조 대상으로 삼는가

| 대상 | 포함 여부 | 이유 |
|---|---|---|
| 1층 모드 | 포함 | 서버에 설치한다 |
| 2층 모드 | **제외** | 각자 클라이언트에만 깐다. 서버에 없는 것이 정상이다 |
| 3층 모드 | 포함 | 서버에도 설치한다 |
| `modpack.dependencies` | 포함 | 3층 모드가 요구하는 라이브러리라 서버에도 깔려 있다. 빼면 `Jotunn` 이 유령으로 뜬다 |
| `BepInExPack_Valheim` | **제외** | 모드 로더 자체다. 플러그인 목록에도 `Loading` 로그에도 등장하지 않는다 |

## config 를 만들지 않는 것이 정상인 모드

`MultiUserChest` 는 설정 항목 자체가 없다. DLL 에 `BepInEx.Configuration` 참조가 없는 것으로 확인했다(`docs/guides/mods.md` 의 "현재 상태" 표). config 가 없는 것이 정상이다.

이런 모드를 그대로 두면 매번 "초기화 실패" 로 뜬다. **정상인데 경보가 울리면 사람이 경보를 무시하게 되고, 그러면 진짜 사고를 놓친다.** 그래서 예외를 둔다.

예외는 `admin/lib/mod-identity.mjs` 의 `IDENTITY_OVERRIDES` 에 `configOptional: true` 로 적고, **왜 예외인지 근거를 함께 적는다.** 근거 없이 예외를 늘리면 감지가 무의미해진다.

현재 예외인 모드는 셋이다.

| 모드 | 근거 |
|---|---|
| `MSchmoecker/MultiUserChest` | 설정 항목 자체가 없다. DLL 에 `BepInEx.Configuration` 참조 없음 |
| `ValheimModding/Jotunn` | 모딩 라이브러리. 자기 설정을 만들지 않는다 |
| `shudnal/ConditionalConfigSync` | 다른 모드가 값을 등록해야 파일이 생긴다 |

화면에서는 이 경우 config 칸에 `없음(정상)` 으로 표시하고 그 아래에 근거를 적는다. 판정을 조용히 삼키지 않고 이유를 보여준다.

## 이름이 서로 다른 문제

같은 모드가 자리마다 다른 이름으로 나타난다.

```
mods.json 의 id     ServersideQoL_AutoProcess
plugins 의 파일명     ServersideQoL.AutoProcess.dll
로그의 플러그인 이름   ServersideQoL.AutoProcess
config 파일명         ArgusMagnus.ServersideQoL.AutoProcess.cfg
```

대부분은 영숫자만 남기고 소문자로 정규화하면 이어진다. 이어지지 않는 둘만 예외표에 적었다.

| 모드 | 왜 예외인가 |
|---|---|
| `WackyMole/WackyEpicMMOSystem` | DLL 하나가 플러그인 두 개(`EpicMMOSystem`, `EpicMMOSystemUI`)로 등록된다 |
| `Digitalroot/Digitalroots_Slope_Combat_Assistance` | 패키지 이름에는 소유격 s 가 붙지만 DLL 과 config 에는 없다 |

파일명 짝짓기는 **포함이 아니라 끝나는지**로 본다. 단순 포함으로 하면 `ServersideQoL` 이 `ServersideQoL.AutoDoors.dll` 에도 걸려서, 프레임워크 본체가 사라져도 모듈 파일 때문에 설치된 것처럼 보인다.

## 모드를 추가했을 때

`data/mods.json` 에 새 모드를 넣고 이 탭을 열면 바로 대조된다. 이름 정규화로 이어지지 않으면 "미설치" 나 "유령 모드" 로 뜨는데, 그때 `IDENTITY_OVERRIDES` 에 실제 파일명과 로그 이름을 적어 준다. 값은 추측하지 말고 컨테이너에서 직접 읽는다.

```bash
docker exec valheim sh -c 'ls -1 /config/bepinex/plugins'
docker exec valheim sh -c 'ls -1 /config/bepinex/*.cfg'
docker logs valheim 2>&1 | grep 'Loading \['
```

# 로그 탭

컨테이너 로그를 필터링해서 본다. 최근 4000줄을 읽어 필터를 걸고, 그중 최근 것만 보여준다. 전체를 다 쏟지 않는다.

| 필터 | 내용 |
|---|---|
| 오류와 경고 | `Error`, `Fatal`, `Warning` 과 `Exception`, `failed` 가 든 줄. **기본값** |
| 모드 로딩 | `BepInEx`, `Loading [`, `plugins to load`, `patcher plugins` |
| 접속과 퇴장 | `ZDOID`, `Closing socket`, `RPC_Disconnect`, `Got connection` |
| 전체 | 거르지 않는다 |

문자열 검색으로 더 좁힐 수 있다. 검색어를 넣고 Enter 를 누른다.

## 비밀값 가리기

로그에는 서버 실행 인자가 섞일 수 있다. 화면으로 나가기 전에 서버 쪽에서 가린다. 두 겹이다.

1. **알려진 값**: `server/.env` 와 `agent/.env` 에서 키 이름이 `PASS`, `PASSWORD`, `TOKEN`, `SECRET`, `KEY` 에 해당하는 값을 읽어 문자열 그대로 지운다. 값 자체는 프로세스 안에만 두고 어떤 응답에도 싣지 않는다
2. **모르는 값**: `-password X`, `TOKEN=X`, `ghp_...` 같은 패턴으로 지운다

둘 다 필요하다. 패턴만 쓰면 비밀번호가 맥락 없이 한 단어로 찍힌 줄을 놓치고, 값 목록만 쓰면 새로 생긴 토큰을 놓친다.

가린 자리에는 `[가려짐]` 이 남는다.

> 비밀번호가 4글자 미만이면 가리기에서 제외한다. 짧은 문자열을 지우면 로그 전체가 `[가려짐]` 으로 뒤덮여 읽을 수 없게 되기 때문이다. 반대로 비밀번호가 흔한 짧은 조합이면 무관한 줄까지 가려질 수 있다. 읽기에 불편할 뿐 유출은 아니다.

# 백업 탭

백업 파일 목록을 최신순으로 보여준다. 시각, 경과, 크기를 적는다.

경로는 코드에 박지 않고 `server/docker-compose.yml` 과 `server/.env` 에서 읽는다.

```
BACKUPS_DIRECTORY: "/backups-out"                 컨테이너 안 경로
- ${BACKUP_HOST_DIR:-./backups}:/backups-out      호스트 경로 매핑
```

compose 를 고쳤는데 패널이 옛 경로를 보고 "백업 없음" 이라고 말하면 그것이 가장 나쁜 거짓말이다. 그래서 매번 다시 읽고, 어느 출처에서 온 경로인지도 함께 표시한다.

## 읽기만 한다

**이 패널은 백업을 지우거나 되돌리지 않는다.** 월드 데이터를 건드리는 기능은 만들지 않았다. 그런 실수는 되돌릴 수 없다.

복원이 필요하면 백업 zip 을 직접 풀어 넣는다. 절차는 `docs/guides/world-migration.md` 에 있다.

# 만들지 않은 것

## 설정값 편집

스펙 9절이 "자주 쓰는 설정값 편집" 을 적어 두었지만 이번에는 넣지 않았다.

이유는 우선순위다. 절반만 동작하는 기능을 여러 개 만드는 것보다 드리프트 감지, 서버 제어, 로그, 백업이 확실히 동작하는 편이 낫다고 판단했다.

설정 편집을 만든다면 스펙 9절이 정한 범위를 지킨다. **모드 설정 파일 전체를 UI 로 만들지 않는다.** `PlantEverything` 설정만 23KB 에 항목이 수백 개다. 자주 건드리는 것만 노출한다.

- 서버 이름, 비밀번호
- `ExtraSlots` 의 슬롯 켜기와 끄기
- `AutoProcess` 의 동작 반경

그 외는 "설정 파일 직접 열기" 로 처리한다.

## 모드 추가, 끄기, 켜기

스펙 9절의 모드 탭에 있지만 넣지 않았다. 모드 설치는 파일을 넣고, 소유권을 고치고, 재시작하고, 로그로 검증하는 과정이다(`docs/guides/mods.md` 의 "서버에 모드를 설치하는 절차"). **모드 제거는 추가보다 위험하다.** 그 모드가 월드에 만든 오브젝트가 남아 있으면 로드 시 사라지거나 오류가 난다.

지금은 사람이 절차를 따르고, 패널은 결과를 대조하는 역할만 한다. 대조가 먼저 확실해진 다음에 자동화를 얹는 것이 순서다.

# 구조

```
admin/
  server.mjs            HTTP 서버, 라우팅, 작업 진행 관리
  lib/
    collect.mjs         **부수효과가 여기에만 있다.** docker 실행, 파일 읽기
    drift.mjs           드리프트 판정 (순수 함수)
    mod-identity.mjs    이름 정규화와 예외표 (순수 함수)
    logfilter.mjs       로그 파싱, 필터, 비밀값 가리기 (순수 함수)
    backups.mjs         백업 목록 정리, compose 경로 해석 (순수 함수)
    control.mjs         서버 제어 허용 판정 (순수 함수)
  public/               브라우저가 그대로 읽는 정적 파일. 빌드 단계가 없다
```

판정은 전부 순수 함수다. 도커를 실행하지 않고 입력만 받아 결과를 낸다. 그래서 서버 없이 테스트할 수 있다. `agent/lib/collect.mjs` 가 상태 조립에서 쓰는 것과 같은 방식이다.

## 테스트

루트 `npm test` 에 포함된다.

| 파일 | 대상 |
|---|---|
| `tests/admin-drift.test.mjs` | 판정표의 여섯 경우, config 예외, 계층 필터, 이름 짝짓기 |
| `tests/admin-logfilter.test.mjs` | 기동 블록 선택, 비밀값 가리기, 필터 |
| `tests/admin-backups.test.mjs` | 목록 정리, 크기와 경과 표기, compose 경로 해석 |
| `tests/admin-control.test.mjs` | 확인 없는 요청 차단, 접속자 있을 때 재확인 |

도커를 실제로 실행하는 부분은 테스트하지 않는다. 그 경계를 얇게 유지하는 것이 `collect.mjs` 를 따로 둔 이유다.

## API

화면이 쓰는 경로다. 직접 호출해도 된다.

| 메서드 | 경로 | 내용 |

# 문제가 생기면

| 증상 | 확인할 것 |
|---|---|
| 페이지가 안 열린다 | 터미널에 서버가 떠 있는가. 포트가 겹치지 않는가 |
| `403` 과 안내 문구가 뜬다 | 주소창이 `127.0.0.1` 이나 `localhost` 인가. 다른 이름으로는 못 연다 |
| 모드 대조가 "컨테이너가 돌고 있지 않다" | 서버 탭에서 시작한다 |
| 전부 "로드 안 됨" 으로 뜬다 | 로그에서 기동 블록을 못 찾은 것이다. 컨테이너를 오래 켜 두어 기동 로그가 밀려났을 수 있다 |
| 새 모드가 "미설치" 나 "유령" 으로 뜬다 | 이름이 정규화로 이어지지 않는 경우다. 위 "모드를 추가했을 때" 참고 |
| `patcher 1개 로드` | 패처 DLL 문제가 재발했다. `docs/guides/mods.md` 의 "패처 DLL 문제" 참고 |
